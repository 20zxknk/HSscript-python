# 决策：缺陷台账用原始日志做证据

Status: implemented

## 问题

修 bug 最容易犯的错是“以为修好了”：离线测试全绿，真机上一步都没走。原因不是不认真，
而是判断“修好”的那个依据本身可伪造——只要写一句“已验证”，谁也不知道当时屏幕上
发生了什么。

## 决定

每条缺陷一个目录，`logs/` 里放那一局的**原始文件**，文件名保持原样：

```
logs/mouse.jsonl            我们点了哪儿
logs/recommendations.jsonl  盒子当时要什么
logs/powerlog_story.md      游戏实际发生什么
```

三份能互相对上，才允许标「已修（实机验证）」；缺一份只能记「已修」。

机器能查的部分要说清楚，免得高估：
[`tests/test_bug_book.py`](../../tests/test_bug_book.py) 只检查 `logs/` 里
**文件名**是否含 mouse / recommend / story 三类；
[`scripts/bug_index.py`](../../scripts/bug_index.py) 检查 front-matter 与
`verify.build` / `verify.logs` 是否写了。**“三份内容是不是同一局、能不能对上”仍然
是人工判断**——脚本判不了，所以那条结论的担保人是人，不是门禁。

## 后果

证据留在仓库里，任何人（包括几个月后的我）都能重新核对当时发生了什么，而不是相信一句
结论。规则的执行从“凭自觉”变成“提交时被拦”。

代价是仓库体积：每局三份日志，几百 KB 起。真机那一层也进不了 CI——CI 里没有炉石、
没有盒子、没有那台机器，所以只能人工跑一局再回填日志；自动化能管的只是“回填的日志
是否齐全、是否互相矛盾”。

今天暴露的另一个代价：这套机制能检查“日志在不在”，检查不了“日志是否真的支持那个
结论”。BUG 07 标了「已修（实机验证）」，日志也齐，但换一种开局（后手、实体落定晚）
就读不到起手张数——假阳性是靠后来拿真机日志重跑才发现，不是靠台账自己发现的。
