# 决策：三层架构——日志进、盒子决策、鼠标出

Status: implemented

## 问题

炉石没有官方 API。能拿到的只有三样：游戏自己写的日志（`Power.log` /
`LoadingScreen.log` / `Screen.log`）、网易盒子（HSAng）算好的推荐、以及一个真实窗口。

这三样东西的可靠性和变化速度完全不同：日志格式随游戏版本变；盒子的推荐是另一个
进程里的一段字符串；鼠标落点必须落在真实窗口的真实像素上。如果把它们混在一处，
任何一处改动都要重新验证全部行为——而验证一次要打一局真机，五到十分钟。

## 决定

严格分三层，层与层之间只通过两个数据结构通信。

**输入** `src/hspy/input/` 只做解析：日志文本 → `GameState`。它不知道盒子的存在，
也不碰鼠标。日志里读不到的东西（比如对手手牌）它不会去猜。

**决策** `src/hspy/decision/` 只做转发：盒子说什么，翻译成 `Plan`。它不自研战术。
盒子没给推荐时脚本就停在那里等——这是刻意接受的，用自己半吊子的判断替代盒子的
胜率模型，只会让结果更差且无法归因。

**输出** `src/hspy/output/` 只做执行：`Plan` → 真实鼠标点击。它不知道游戏规则，
只认坐标、槽位和点击时机。

## 后果

分层换来了可替换和可回放：输入层可以只喂一份留档日志做离线重演（本机 `test/` 下 47 个对局目录、41 份 run.log 就是这么用的；这些目录没有入库）；输出层可以在 dry-run 下完全不碰鼠标；决策层可以换成
别的盒子而不动另外两层。

代价也要记清楚。三层各自维护着「另一个数据结构」的字段，`GameState` 加一个字段
要同时核对决策层怎么读、输出层怎么用。盒子没推荐时脚本完全不动，没有自己的策略
兜底——网络抖一下或者盒子崩了，这一局就废了。层间边界在真机上也不绝对：换牌阶段
读起手张数、选择面板点哪一张，都是「解析」和「执行」同时依赖同一份临时状态，
这类地方出错时，日志里看不出该算哪一层的责任。

**没有选的两条路**：一是单层直写，最早就是那么写的，问题是同一份 `Power.log`
重放两次得到的点击序列可能不同（中间夹着实时读取的状态），没法复现问题；二是
自己在脚本里算战术，能摆脱盒子依赖，但要重写整套卡组/斩杀/解场判断，成本等于再写
一个盒子，收益却只是一个进程。
