# 决策：不注入游戏进程，frida 只挂盒子

Status: implemented

## 问题

注入式方案（BepInEx / HsMod 那一类）能读到全部游戏状态、还能直接调游戏内部方法，
看起来比解析日志强得多。代价是它必须对着反作弊打补丁：改了游戏内存、挂了钩子，
就要一直跑在检测的阴影里，而且一旦游戏更新，全部失效。

我们需要的其实只有盒子的推荐文本——而盒子本来就在读游戏内存。

## 决定

绝不注入炉石进程。历史上 Frida 注入游戏导致过崩溃，那条路彻底不走。

允许 frida 挂 `HSAng.exe`，只钩它的 `Qt5Core` 字符串层，把推荐明文读出来；除此之外
不动盒子。

不碰反作弊：作者库里的 `acHook`（阻止游戏反作弊）保持关闭，`PREVENT_AC` /
`ALLOW_GAME_INJECT` 这类开关全部维持默认。

## 后果

游戏侧在我们眼里是一个黑盒，只通过它自己写的日志观测——这意味着对手手牌、牌库顺序
这类内部信息拿不到，所有策略只能基于公开状态。

换来的是一条干净的责任边界：如果出问题，要么是日志解析错了（我们的 bug），要么是盒子
没推荐（环境问题），不会出现“我们改了游戏内存导致它行为异常”这种无法归因的情况。
游戏更新时我们只需要跟着日志格式变，不需要对抗反作弊的更新。

代价是桥很脆：盒子不在、或者它换了内部实现（不再是那几个 Qt 字符串调用），桥就断，
脚本完全停摆。
